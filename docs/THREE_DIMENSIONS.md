# The hollow garden: next backend cycle

Latest user steering takes precedence over the initial flat-world design: use a genuinely complicated 3D environment, substantial backend progress before verification, rich social and outside interaction, and mechanisms that leave room for discovery. The first FlyWire garden remains a functioning reference. The target dataset is MaleCNS brain plus cord, with full curated connectivity acquired and benchmarked remotely rather than quietly advertised through a tiny female-brain subset.

The direction: a little ecosystem of physical opportunities. Raised ground and ramps, sheltered underpasses, light and shade, rolling and stackable objects, resonant objects, a balance bridge, pendulums, resources that can be carried, and residents whose activity changes what others encounter. Physics creates combinations; predefined gameplay quests do not delimit the space. The human has a physical hand/spring, sound and light instruments, and can offer, move or release objects. Residents receive the hand through sensation. Social behavior can develop through visible motion, contact, signaling and shared artifacts without injecting private account/creature IDs into cognition.

## Implementation seam

`chreatures/physics.py`: `PhysicsWorld(seed=7, spec=None)` with actual MuJoCo 3D dynamics, z-up meters. No browser physics substitution. Existing World2D remains in world.py. World3D owns native model/data, entity spec/component data, physiology and RNG. Serialize full MuJoCo integration state (`mjSTATE_INTEGRATION`) plus model specification, mutable geom/material/constraint state, component values, schedules and RNG. Never silently load a different engine/source revision as exact continuation.

`data/habitats/hollow-garden.json`: declarative entity/material/component definitions. Entity shape, physical material and attached biological components are independent fields. Supported geometry is a composable set, not an enumeration of objects with hand-coded intentions. Include static boxes/ramps/arches, free spheres/boxes/capsules, hinged seesaw and resonant pendulum, food/scents attached to physical objects. Limits are numeric/capacity constraints; no world script makes residents seek food or play.

Prototype body: an explicitly synthetic crawler with physical free-body pose, inertia, gravity, contact traction and posture stabilization. Contact-propulsion models ciliary traction; no teleporting or forcing a fixed z. Render actual dynamic pose. Keep body construction and actuation isolated so an articulated NeuroMechFly body can replace it once the upstream integration earns its cost. Body mechanics are supplied capabilities, not claims of learned locomotion. Do not pretend decorative appendages are simulated joints.

Initial API is parallel to World2D: bodies list (id/name/x/y/z/heading/radius/energy/gut/fatigue/speed/angular_velocity/age/color), `.sense(id)` exposes 16x4 actual3D ray RGB/proximity, 2x3 local scent, 3tone sound, 2touch, local shade and proprioception only; richer `retina3d`/contact normals/angular/linear velocities can be added. `.advance(actions,dt=.05)` takes forward/turn/eat/signal plus optional grip, gaze_pitch and lift/vertical traction, integrates0.005s physics substeps, returns nutrition/contact/distance outcomes. Root brain/runtime will route richer channels. `.view()` exposes `dimension:3`, physical geometry types/sizes/positions/quaternions/material colors, entities/components for rendering, actual joint transforms if present. `.snapshot()`/`.restore()` keeps everything necessary, simple useful integrity checks after module works.

Caregiver commands: add physical entity from shape/material/components preset, move by bounded force/spring through a cursor hand (not instant relocation while time advances), release, impulse within physical bounds, signal at3D position, light. Authoring spec changes are separate from lived actions. Object operations and simulation advancement remain ordered by one authority.

## Coupling and learning work

Current hardcoded warm-color avoidance and gradient attraction are bootstrap motor policies, not the target autonomy. Build a trainable interface over measured circuit activity, personal associative/context memory and bodily needs. Use bodily resource change, controllable/predictable novelty and contact consequences to learn actions. Train developmental ensembles on the AMD GPUs; inherited readouts/plasticity rules and personal adaptations stay separate. Hold-out capabilities after substantial implementation: negotiating unseen3D geometry, manipulating an unfamiliar object, learning a sensory exchange, and persisting acquired habits. Inspect failures and use them to change the organism.

Native GAM and Weave already execute on actual project state; integrate their results where they help investigation. Avoid growing dashboard taxonomy faster than the organism. First build the3D backend and reciprocal learning, then run meaningful integration checks.
